# DeepWrite 长篇写作迁移设计

## 目标与边界

长篇写作以独立的 `deepwrite.long-book` 项目类型接入 DeepWrite。它参考
Write Claw 的长篇结构，但复用当前 DeepWrite 已验证的会话、审批、CAS、
事务、素材/技能绑定和主题组件。短篇 `book` 与剧本 `script` 的 schema、
目录、会话、设置和保存链路不扩展、不分支、不复用长篇持久化状态。

隔离原则：

| 层 | 长篇实现 | 与短篇/剧本的边界 |
| --- | --- | --- |
| 契约 | 独立 LongBook、LongWorkspace、LongLedger、LongAgentSettings | 不扩展 WorkspaceType/BookSchema/ScriptSchema |
| 存储 | 独立项目目录、manifest、索引、事务与 Catalog | 不读取或改写短篇/剧本项目文件 |
| 会话 | bookId + long agentId + root + chapterId | 不复用短篇/剧本草稿、审批或恢复 key |
| API | `deepwrite.long.*`、`longAgents`、`longAgentTeams` | 独立 IPC 命令和 Preload schema |
| Renderer | 独立三栏工作区和管理器 | 仅复用主题变量、PopupSelect、toast 等基础组件 |

## 长篇结构

工作区包含五个可见根节点和六个主智能体：

1. 世界观：可扩展分类；列表型分类是目录，每个条目以独立 Markdown 为内容权威，
   文本型分类仍以单份 Markdown 为内容权威。
2. 人物设计：人物元数据加核心档案、关系、当前状态、历史四文件。
3. 剧情设计：卷、剧情弧、章卡、故事事件、事件连接、叙事落点和伏笔线。
4. 专家正文：章节写手只生产正文；章末人物状态和下一章接续包是只读的账本投影。
5. 连续性账本：以正文为证据，生成并管理当前事实、知识边界、开放事项、章末输出、
   人物连续性文件、章节流水和可逆审计记录。
6. 主智能体分别为世界观、人物、剧情、正文统筹、章节写手和连续性账本。

实体使用稳定 ID；文件路径由稳定 ID 推导，标题和排序变化不引起路径变化。
工作区索引只保存结构与文件引用，正文按需分页读取。新文件 revision 使用
UTF-8 字节长度和完整 SHA-256 的 `v2` 格式；旧 `v1` 8 位 revision 只用于
兼容读取，并在后续写入时升级。

世界观列表型分类不再保存整类聚合 Markdown：分类索引保存稳定条目 ID、标题、
顺序和各自文件引用，创建、写入、局部替换、删除与重排均按条目执行。旧本地项目
和旧可移植包中的聚合列表会在打开或导入时事务性拆分为独立条目文件；文本型分类
不做拆分。

人物设计沿用同一条“索引只存结构、独立文件保存正文”的原则：人物列表索引保存
稳定人物 ID、姓名、分组、顺序和别名，文件索引按人物 ID 关联核心档案、人物关系、
当前状态和历史轨迹四份 Markdown。人物智能体通过按人物与文档角色区分的 typed
工具创建、读取、覆盖或局部替换，不读写整个人物列表的聚合正文。

世界观、人物核心档案、剧情弧、章卡、叙事落点和伏笔触点表达的是“设计意图”；
连续性账本表达的是“正文截至某章实际成立的事实”。二者不得互相冒充：

| 上层区域 | 可编辑的设计态 | 来自账本的事实态 |
| --- | --- | --- |
| 人物 | 核心档案、初始关系设计 | 当前事实、当前关系、当前状态、历史轨迹及来源提交 |
| 世界观 | 世界规则与分类资料 | 已在正文中成立或揭露的世界事实及知情边界 |
| 剧情 | 卷/弧/章卡、事件、叙事落点、伏笔计划 | 实际推进结果、伏笔执行状态和仍未闭合事项 |
| 专家正文 | 章节正文 | 章末人物状态和下一章接续包 |

上层区域不复制、嵌入或展示一份独立真相。连续性事实只在连续性账本工作区中
通过稳定 ID 聚合，并可回到产生该事实的章节提交和正文证据；人物、世界观和
剧情设计页面保持纯粹的设计与编辑界面。

## 修改与审批

Agent 只有查询能力和“形成提案”的能力，不直接写盘：

1. Runtime 从 Core 读取最新索引。
2. typed domain tool 接受业务字段，不接受路径、文件 ID、时间或 revision。
3. Runtime 生成稳定 ID、规范文件引用、CAS revision 和精确影响集。
4. Renderer 展示完整结构变化、文件全文、before/after 和级联影响。
5. 用户批准前先保存当前编辑器；Core 再执行 schema、权限和 CAS 校验。
6. Store 通过可恢复事务一次提交业务文件、索引和 manifest。
7. 成功后同步编辑器基线；冲突时保留脏稿并提示重新核验。

剧情智能体可以创建章节及三份固定文件容器，但不能通过通用结构工具写正文。
章节写手的提案只写正文；人物状态和接续包由连续性核验在提交事务中生成，不能
由编辑器、写手工具或通用文档工具直接改写。

Renderer 在保存审批前先锁定编辑器，并在保存后再次核对活动书籍和提案身份，
防止双击审批、保存期间继续编辑或上下文切换造成旧快照落盘。串行计划运行时，
只有与当前书籍、章节、阶段、Agent、session 和 run 全部匹配的章节/账本提案
可以批准或影响计划状态；此前残留的结构、错章或旧会话提案不能推进计划。

所有长篇写入都经过项目级跨进程独占锁；事务进入 prepared 状态后会在真正
替换文件前重新校验全部前置 revision。锁文件包含进程和随机身份，只有确认
持有者已退出且锁的 inode/身份未变化时才可回收，避免过期锁回收中的 ABA
误删。等待方读取锁时若持有方恰好完成释放，会把路径消失/换代视为重试信号，
不会把正常并发转换成 `ENOENT`。manifest、索引、Markdown 和账本记录分别
执行角色化字节上限，拒绝超限内容进入事务。

## 章节编排

长篇只允许 `chapter`、`arc`、`volume` 三种写作范围，不允许整本并发写作。
章节始终按卷序和卷内叙事顺序串行处理：

1. `empty`：正文为空，启动新的章节写手运行。
2. `ready_to_commit`：正文非空，正文成为待核验的唯一事实证据。
3. 章节正文提案批准、保存和刷新成功后，才进入连续性阶段。
4. 连续性智能体逐域核验正文并生成类型化变更、章末状态和接续包。
5. 连续性提案批准后，Store 在一个事务中写入所有投影、审计记录和索引水位。
6. 提交成功后才推进范围内下一章；任一步失败都停在当前章，可重试但不能跳章。

旧版 `partial` 与“正文/人物状态/交接三件套齐备”判定只用于兼容已有调用和历史
记录，不再是当前编排的生产路径。

每章写手与连续性核验都使用 fresh session/run，避免上一章上下文污染。
取消计划时先隔离对应 session 并清除其待审提案，再失效编排 epoch；尚未取得
run ID 的请求会立即换 session，并在受理结果迟到后补发中止。已经取得 run ID
的运行先捕获中止请求再换 session，因此迟到事件不能重新入队或启动下一阶段。

## 连续性账本

连续性账本是正文事实的唯一权威源，不再只是提交日志。它分成五个工作区：

1. **待核验入账**：锁定连续下一章，以正文为唯一证据，列出需承接的开放事项。
2. **当前事实快照**：按人物、关系、世界、剧情、伏笔展示截至当前提交的有效事实。
3. **剧情与伏笔执行**：对照计划记录正文实际执行、遗漏、推进和闭合结果。
4. **信息揭露与知识**：区分世界真相、读者所知、人物/势力所知、怀疑和误导。
5. **章节流水与接续**：按提交查看本章变化、来源证据、章末状态和下一章接续包。

每次 v3 提交必须包含：

- 非空提交说明和时间线、人物、势力、境界、伏笔、连续性六段摘要；
- 人物、剧情、伏笔、世界、知识、开放事项六域核验结果；即使无变化，也必须
  明确标注 `unchanged` 或 `not_applicable` 并说明证据；
- 本章每个叙事落点和伏笔触点的 `committed` / `missed` 判定及非空正文证据；
- 类型化事实变更：稳定 fact ID、领域、稳定 subject ID、字段、当前值和正文证据；
- 读者、人物或势力对某事实的知识级别变更；
- 开放事项的新建、推进、闭合或放弃，以及它引用的事实和证据；
- 完整章末人物状态与结构化下一章接续包。

Store 根据该提交原子生成三类结果：

- **权威投影**：更新 `facts`、`knowledge`、`openLoops`、投影水位和最新接续包；
- **资料映射**：写入本章只读人物状态/接续包；人物事实变化同步人物当前状态并
  追加历史，人物关系变化同步关系资料及历史；
- **永久审计**：保存所有 before/after、来源章节、来源提交和正文证据。

人物历史只能由后端追加，并自动写入章节 ID、提交 ID 和提交时间。连续性账本
不能改写人物核心档案、世界设计文档、全书线或剧情计划；这些上层资料仍表达
创作设计，账本只通过稳定对象 ID 提供事实映射。首次提交后，人物关系、当前
状态和历史轨迹由账本接管，不能在编辑器外绕过账本直接修改。

每条可逆记录保存精确 before/after；只允许回滚最后一条可逆提交。回滚会在同一
事务中反向恢复事实、知识、开放事项、最新接续包、人物连续性文件和本章两份
章末输出，正文不回滚。已提交正文、账本生成输出和账本接管的人物文件固定索引
revision，检测到外部篡改立即停止，而不是静默接纳。

已提交事实形成不可跨越的结构锚点：对应章节、卷序、剧情弧、事件、人物引用、
叙事落点、伏笔节拍和真相事件不能通过重排或级联删除改变。

提交和回滚会在同一事务中复核完整 pinned 集合：既有账本记录、已提交正文、
账本生成的章末输出以及账本接管的人物连续性文件都必须与索引一致。Runtime
使用 Core 刚读取的实时 revision 构造提案，模型输入中的路径、文件 ID 和
revision 不会成为写入依据。可移植包导入还会从 v3 记录重放完整投影，并与
索引末态、章节输出和提交水位交叉核对，防止只篡改快照而绕过审计链。

## Write Claw 迁移

迁移始终在同级 staging 目录完成校验，再原子重命名为正式项目；源文件只读，
符号链接和硬链接均拒绝。

- v1/v2：已提交章缺少现代审计字段时，生成稳定、只读、不可逆检查点，并使用
  明确的未知时间占位。
- v3–v5：标记已提交的章节必须有 commit ID、有效提交时间和对应时间线证据；
  缺任一项即拒绝迁移。
- 有完整提交链时恢复连续叙事前缀、落点/伏笔判定和账本记录。没有精确
  before/after 的旧记录绝不标记为可逆。
- 旧绑定、记忆、孤立账本条目、附件和无法结构化的原文以只读、可搜索迁移证据
  保留，不静默丢弃。
- 每个 drop、merge、coerce 和未解析引用都记录原始值、来源位置、决策与
  完整 ID 映射；原始源文件快照一并保留，迁移结果可追溯而不是只保留摘要。
- 参考项目每章产生一份 stage 和三份正文投影；经典 ZIP 可读取至 65,534 个
  条目，并同时受 256 MiB 压缩包、512 MiB 总解压量、64 MiB 路径总量和异常
  压缩率约束。权威 book/workspace JSON 单项上限为 128 MiB，普通附件仍为
  32 MiB。
- 超量世界观条目、换行标题、保留标记和超大正文会保守规范化，完整原值写入
  只读证据。大量小附件按 UTF-8 字节预算聚合成可搜索证据包，不会耗尽
  10,000 个世界观索引槽；常规迁移仍保留“书籍记忆”“账本”等原语义标题。

兼容的可移植包包含 manifest、索引、全部 Markdown 和账本记录的 SHA-256；
导入时交叉核对 record 与 index entry、提交顺序、章节、判定集合及 revision，
旧版聚合世界观列表会在完整性校验后拆分为独立条目文件，再通过 staging 目录
原子落盘。当前客户端只保留该格式的安全导入，不再提供可移植包导出命令或覆盖
已有导出文件的流程。

## 设置与权限

长篇六角色和长篇智能体团队使用独立配置存储。系统提示词、快捷语、模型和读取
范围可配置；写入根和能力由内置角色固定，不能在设置中扩大。子智能体继承所属
长篇角色的受限工具，修改仍进入同一审批链。

Renderer 以每本书的单调刷新时钟原子发布索引和摘要；刷新失败时暂停发送并
提供重试，不用半新半旧状态启动智能体。串行计划运行期间统一阻止跨书切换、
导入迁移、结构和绑定修改、回滚、移除以及对话切换。长篇角色/团队的加载、
保存、错误和重试状态与短篇、剧本完全隔离。

## 验收

交付前至少验证：

- 长篇创建、关闭、重开、搜索、导入和移除；
- 世界观、人物、剧情全部 typed CRUD、重排和级联预览；
- chapter/arc/volume 串行写作，正文 readiness、fresh session 和失败停止；
- 正文单独写入、账本原子生成章末状态/接续包、最后提交回滚和导入后回滚；
- 五区连续性工作台、稳定来源跳转，以及账本事实与上层设计页面的界面隔离；
- 人物/关系/世界/剧情/伏笔事实、读者与角色知识、开放事项的跨章演进；
- 500+ 文件事务、200+ 章节 Catalog、Unicode 分页和搜索；
- 外部篡改、CAS 冲突、跨进程并发、锁 ABA、符号链接、硬链接和事务恢复；
- 长篇设置持久化和崩溃草稿恢复；
- 全仓 typecheck、lint、test、build、Renderer smoke；
- 同一验收中重新运行短篇和剧本的创建、写作与保存回归。
